# 深く読む CPU（engine/deepcpu.ts）

エンドレスマッチの強い段階に使う CPU。今の easy / normal / hard（`cpu.ts` の `chooseMove`）の手は変えず、別の入口 `chooseDeep` にした。画面・サーバーにはまだ組み込んでいない（2026-10-17）。

## 使い方

```ts
const t = chooseDeep(viewFor(state, p), { nodes: 10000 }, rng);
if (t.use) state = useSkill(state, t.use, rng);   // 手番の頭に使うスキル
if (t.move) state = playMove(state, t.move.r, t.move.c, t.move.kind, { king: t.move.king, vice: t.move.vice });
// use だけで move が null なら、使った後にもう一度 chooseDeep を呼ぶ（偵察・運命の輪・巻き戻しの結果で読みが変わる）
```

- 強さのつまみは `DeepBudget.nodes`（1 回の判断で `playMove` を呼ぶ回数の上限）。壁時計は使わないので、同じ view・同じ乱数・同じ予算なら同じ手（`test/deepcpu.test.ts`）。時間はおよそ予算に比例する（下の表）
- ほかに `maxDepth`（既定 8）・`width`（根より下で読む手の数、既定 16）と、評価の係数 `DeepWeights`（既定 `DEEP_WEIGHTS` = tempo 0.8・gauge 0.7・own 1）
- 測定: `cd web && npm run balance -- deep 400 deep:10000 hard [並列数=2] [プリセット=skill]`。A・B は easy / normal / hard / `deep:予算[:幅][:dN][:tempo=][:gauge=][:own=]`。子プロセスに分けて並列に回す（`scripts/deep-run.mjs` → `scripts/deep.mjs` → `scripts/deep.ts`）。局 i は種 i + 1、偶数局は A が先手。ファンが回るので並列数は 2 まで

## 探索

- 反復深化のアルファベータ（自分の手番は max、相手の手番は min。連続行動の 2 手目・パスもそのまま）。手の適用はエンジンの `playMove` / `useSkill` を使い、ルールを写し直さない
- 根の手はすべて読む: 使うスキル（なし・持っているカード）× 置く手 × 王を指定するか。王の指定は `chooseLookahead` と同じく期限内の各手で「残りの手数分の 1」の確率で候補に足し、指定しない最善以上のときだけ選ぶ。期限の手は選んだ手に `king: true`
- 根より下は手の見込み（すぐ取れるダメージ＋回復＋罰）の上位 `width` 手、スキルを使う手は `width / 2` 手
- 予算が尽きたら、その深さで読み終えた根の手（前の深さの最善から読む）の値で選ぶ。同点は乱数
- 末端の評価（自分から見て）= 体力差 ＋ 返した相手の王・副将の罰の見込み ＋ gauge ×（カードの価値 × 溜まった割合 の差）＋ 手番の側の符号 × tempo × 手番の人がすぐ取れる最大の得点。決着は ±1,000,000 から 1 手ごとに 1,000 引く（早く勝つ・遅く負ける）
- 副将は選んだ手について `viceWith`（返されないマスにだけ置く。ノーマルと同じ）
- 読むスキル: 強打・全方向・鉄壁・連続行動・回復 2 枚・補充（数字の大きい駒 2 つ。読みの中では 1 つ）は両者とも。王の移し替えは自分の手番の頭だけ（次の手で返されないマスへ、端を優先して 3 つ）。偵察・運命の輪・巻き戻しは乱数や見えない局面に頼るので読まず、`chooseSkillUse` の規則で使う

## 隠し情報

- 入力は `viewFor(state, 自分)` の view だけ。`stateOf` が view から読みの局面を作り直す（`.kings` を読まない。`test/king.test.ts` のソース検査に `deepcpu.ts` と `skillcpu.ts` を足した）
- 自分の王・副将は view の `myKing` / `myVice` から作る（副将の窓の周期は `left` から合わせる）。相手は探索の中で自分の王・副将の場所を知っているものとして読む（慎重側。`own` < 1 で、相手から見える候補に罰を等分する読み方にもできるが、自己対戦では 1 が強かった）
- 相手の王・副将は「もうない」状態にしてエンジンに罰を付けさせず、公開の候補からの見込みを自分がその駒を初めて返したときに足す（同じ駒は 1 回だけ）
  - 王: 候補ごとに 罰 × pk ÷ 候補の数。pk は偵察で特定していれば 1、そうでなければ min(1, 相手の手数 ÷ 期限)
  - 副将: 偵察で特定していればそのマスに 15。そうでなければ pv（`oppVice.set` なら 1、王の期限を過ぎていれば 0.5）× 15 ÷ 候補の数。候補は相手が最近 14 手に置いて一度も返されていない駒
- 巻き戻しの局面（`skills.undo`）は view にないので持たない

## 測定（標準 = id `skill`、2026-10-17）

### 係数の調整（予算 10000 の自己対戦、各 400 局 ±2.5。8 並列で測った）

| 回 | 基準 | 試した値 → 基準に対する勝率 |
|---|---|---|
| 1 | tempo 0.6・幅 10 | tempo 0.3: 45.0 / tempo 1: 59.0 / gauge 0: 46.0 / gauge 1.4: 46.8 / 幅 6: 43.0 / 幅 16: 55.8 |
| 2 | tempo 1・幅 16 | tempo 1.5: 43.8 / tempo 0.8: 61.8 / 幅 24: 51.2 / 幅 12: 57.5 |
| 3 | tempo 0.8・幅 12 | own 0.5: 43.8 / own 0: 45.3 / 幅 16: 57.8 |

→ tempo 0.8・幅 16・gauge 0.7・own 1。自己対戦の比較なので結果はやや非推移的（2 回目は幅 12 が 16 に勝ち、3 回目は 16 が 12 に勝った）。決着の値に手数を入れた後の版と前の版は 予算 3000 で 49.3%（400 局 ±2.5）で差なし。

### 1 手番の時間（ms。スキルを使う判断を含む。相手は hard）

| 予算 | Node 中央値 | 95% | 最大 | workerd 中央値 | 95% | 最大 |
|---|---|---|---|---|---|---|
| 3000 | 30 | 36 | 42 | — | — | — |
| 10000 | 96 | 113 | 145 | 107 | 123 | 529 |
| 30000 | 287 | 335 | 383 | 321 | 358 | 386 |
| 60000 | 575 | 656 | 704 | 635 | 710 | 746 |
| 100000 | 941 | 1058 | 1106 | 1042 | 1174 | 1202 |
| 150000 | — | — | — | 1567 | 1752 | 1823 |

- Node は 1 プロセスだけで（3000〜30000 は 40 局、60000・100000 は 20 局）、workerd は `@cloudflare/vitest-pool-workers` の中で 12 局（手番 189〜230）。どちらもこの Mac（Apple Silicon）。1 局面およそ 10µs で、時間は予算にほぼ比例する
- workerd の 10000 の最大 529ms は最初の手番（JIT の前）
- workerd で 1 手が最大 2 秒以内に収まるのは予算 150000 まで（最大 1823ms）。ただし今の評価では 10000 より上は強くならない（上の直接対戦）ので、使う上限は 10000（workerd の中央値 107ms・95% 123ms）。本番の Cloudflare の CPU はこの Mac より遅いことがあるので、本番に組み込むときに Durable Object の中で測り直す
- 100000 の対 normal と、直接対戦の 100000 対 30000 の最大（約 1,000,000ms）は測定中に Mac が眠った分で、外れ値（中央値・95% には効いていない）

## 未解決

- **予算 30000 が 10000 に負け越す**（400 局で 42.5 ± 2.5%。深さを 6 で止めても 41.5%）。100000 も 10000 に 38.5%（200 局）。対 hard・対 normal では 30000・100000 も 94〜99% 勝つので、弱いのは 10000 を相手にしたときだけ。係数（tempo 0.8・幅 16）を予算 10000 の自己対戦で決めたことが関係していそう: 30000 で tempo を 0.5 にすると 54.5%、深さ 5 で止めると 54.0%（どちらも 200 局 ±3.5 で、50% と見分けられない）。読みを深くすると末端の「手番の人がすぐ取れる得点」の見込み（tempo）の偏りが積み重なる、という見立てだが確かめていない（2026-10-17 の測定で切り分けを打ち切った）
- 直すなら: tempo を深さ・予算で変える／末端で取り合いを 1〜2 手だけ読み足す（静止探索）／30000 の自己対戦で係数を決め直す。どれも直接対戦で 10000 に勝ち越すことを確かめる
- それまでエンドレスマッチの段階に使う予算は 10000 まで
